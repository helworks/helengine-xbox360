# What would make this better

Written 2026-09-16, after the transpiled core booted and a scene built with
the engine's own types drew through the Xenos backend. The order matters:
the first item gates most of the rest.

## 1. This target is not a platform the editor knows about (in progress)

Every other port has a builder project and an entry in the platform registry
pointing at it. PlayStation 1, Dreamcast and N64 each have a `builder/`
directory, and `helengine/user_settings/platforms.json` gives each platform a
`platformId`, a `builderAssemblyPath`, a `playerSourceRootPath`, a
`generatedCoreCppRootPath` and a pinned `engineVersion`. This target has
neither a builder nor a registry entry, so it sits outside the normal build
path entirely.

That is why the scene on screen is built in code. Nothing can cook assets
for this target, stage them, or write a scene catalog, so the demodisc scene
the other consoles run cannot be built for it at all.
`tools/generate-core.ps1` hand-rolls the transpile step and stops there.

Closing this buys three things at once:

- the authored scene instead of a hand-built one,
- a pinned engine revision, so regenerating is deliberate rather than
  whatever the worktrees happen to hold,
- asset staging that a content source can read from an archive embedded in
  the image, replacing `EmptyContentStreamSource`.

The shape to copy is the PS1 port: a C# builder plugin that cooks and stages,
plus a native build script the builder calls. The Dreamcast port's content
stager and cooked-content validator are the closest reference for the
staging half.

**Done so far:** `builder/` holds the platform definition, material cooker,
scene validator, content stager, scene catalog writer and native build
executor, and it compiles against the shared engine checkout and describes
itself. `tools/build-image.ps1` is the single entry point the builder calls,
and it produces a bootable image from a generated core plus a staged content
directory.

**Still missing before the editor can drive a build:** an entry in the
platform registry so the editor discovers the builder, the project's own
supported-platform list, and guest-side consumption of the generated scene
catalog so a cooked scene is actually loaded rather than the scene being
built in code.

## 2. What the scene needs before it looks like the scene

| Gap | State today | What it needs |
|---|---|---|
| Materials | none; vertex colour is derived from the normal | a per-draw constant colour, which means a constant in the pixel shader |
| Textures | `BuildTextureFromRaw` returns null | Xenos texture fetch constants, tiling and formats; the largest single piece left |
| Lighting | unlit | the engine's ambient and directional lights, as the PS1 port did per-vertex through the engine's own light utility |
| Two dimensional drawing | sprites and text report their calls and draw nothing | a 2D path, or the Dreamcast position of stripping the instruction UI on minimal targets |

The colour-from-normal shading is a debugging aid, not a renderer: it makes
a wrong normal or a wrong winding obvious, which is what it was for.

## 3. The risk worth naming

Everything here is verified in the emulator and nowhere else.
`xenia-backend-contract.md` section 8 lists what is emulator-specific:
fences complete when the emulator's command thread reaches them rather than
when the GPU finishes, the swap packet is generated by the emulator's own
kernel call, memory-mapped writes other than the ring write pointer are
ignored, and the time base runs at the host's rate. Each is an assumption on
real hardware.

Two related gaps. There is no frame pacing: the loop runs as fast as fences
retire, so the timing numbers measure the emulator rather than the console,
and it was fast enough that the old alternating clear colour read as a
flashing background. And the image is unsigned, so how it would load on a
real machine is still the open question the plans deliberately refused to
assume.

## Smaller items worth folding in while working nearby

- A validation pass for the current state. `v0.1-validation.md` records five
  launches and a ten-minute run, but it predates the core, so the numbers
  describe an image that no longer exists.
- Mesh storage. Each mesh takes its own 64 KiB physical allocation and there
  is no per-mesh release; `hel_mesh_release_all` runs only at shutdown.
- The texture stub returns null silently. It should report once, the way the
  model path does, so a scene that wants a texture says so.
- Failure paths that exist but have never run: fence timeout, ring overflow,
  physical allocation failure.
- The core compiles against hosted headers because the generated runtime
  includes `<functional>` and `<memory>` unconditionally. Fixing that in
  csharpcodegen would let it compile freestanding and drop libstdc++ from the
  image.

## Recommendation

Do the builder and content packaging first. It converts this from a
demonstration that the path works into the actual game booting, and it is
the prerequisite that makes materials and textures worth building.
