## 3. Runtime resources

Logged at initialisation and every 60 frames (`HEL frame: allocations`,
`HEL frame: allocated bytes`):

| Owner | Size | Purpose |
|---|---|---|
| ring | 0x10000 | command ring (64 KiB, wrap padding per frame) |
| scratch | 0x10000 | read-pointer write-back, fence, VdSwap arguments, fetch constants |
| front buffer | 0x400000 | 1280x720 tiled `k_8_8_8_8` resolve destination (3,686,400 bytes used) |
| mesh | 0x10000 | 24 vertices and 36 indices, big-endian |

Total 4 allocations, 0x430000 bytes, identical in every run below from the
first report to the last. Logging goes through `DbgPrint` with fixed buffers
and allocates nothing; there is no heap in the guest.

CPU submission time per frame is measured with the time base around the
demo's frame function (about 1.5-1.7 ms including the fence wait); GPU
time is only the first frame's submit-to-fence wall time (0x49-0x70 ms,
dominated by shader translation in the emulator). The emulator completes
fences when its command thread reaches them, not at vertical blank, so the
demo runs at several hundred frames per second in the emulator; frame
pacing is not a validated property here.

## 6. Failure diagnostics

Every backend entry point returns a `HEL_ERR_*` stage code
(`src/engine/frame.h`) and logs the failing stage before returning; the
frame loop stops on the first error and the demo logs `frame loop stopped
with=<code>` before shutting video down. Exercised in this record: invalid
video configuration (`v01-invalid`) and, in the triangle evidence, an
out-of-range index rejected by the mesh validator before upload. Present
but not exercised: physical allocation failure, ring overflow
(`HEL_ERR_RING_FULL`, checked per frame against the 64 KiB ring), fence
timeout (5 s poll, `HEL_ERR_FENCE_TIMEOUT`), shader validation failure.

Teardown safety: `hel_frame_present` waits for the frame's fence before
returning, so no GPU work is pending when `hel_video_shutdown` runs; the
shutdown frees the mesh, front buffer, scratch and ring in that order and
reports zero allocations left (`v01-teardown`). The emulator keeps
displaying the last presented frame afterwards, which is why the
frame-limited run still shows the cube.

## 7. Dependency audit

`third_party/manifest.toml` lists every tool used: xenia-canary
(BSD-3-Clause, unmodified binary, source read for facts), devkitPPC
(GPL-3.0-or-later with the GCC runtime exception; only `libgcc.a` is
linked into the guest), Python (PSF-2.0) and the host WinLibs GCC used for
unit tests only. Shader microcode is assembled from original sources in
`shaders/` by `tools/xenos_asm.py`; no Microsoft compiler, header, library,
sample or shader tool is involved, and no third-party code ships in the
image.

## 8. Limitations

- Emulator-only: fence completion, frame pacing and `VdSwap` presentation
  are emulator behaviours (`xenia-backend-contract.md` section 8). Hardware
  validation is the follow-up plan.
- No vsync pacing: the demo submits as fast as fences complete.
- Single mesh, single shader pair, no textures or lighting; the mesh slot
  table holds four meshes.
- The five launches and the ten-minute run were done on one machine and
  one emulator build; the launcher refuses other emulator hashes.
- `tools/run-probe.ps1` (compatibility probe) still has its own launch code
  rather than using `xenia-launch.ps1`.
